Version 2 addendum step 1 (design spec S13.2) -- does cross-fitted temperature calibration of the
two posteriors change the fixed-versus-adaptive picture? Produced by
scripts/run_v2_calibration_check.py. Verbatim output, recorded whichever direction it points
(design spec S13.6).

Dev-only: run_calibrated_four_arm_comparison splits with fusion.holdout.split_dev_test and keeps the
dev half (Studies B, F, L) alone. Study N is not read here. This result was produced after the
one-shot holdout evaluation had already been run and recorded, so it could not and did not inform
any choice made in that evaluation -- it is the S13.2 checkpoint being reported late, not re-opened.

Result: calibration does not rescue the adaptive arm. For gpt2 the calibrated adaptive arm LOSES to
the fixed arm and the 95% CI excludes zero; for ngram5_kn it gains a little but the CI includes
zero. The primary analysis's fixed-beats-adaptive finding is therefore not an artifact of feeding
the reliability estimator uncalibrated posteriors.

Both fitted temperatures exceed 1, i.e. both sources were overconfident and calibration flattened
them: the neural posterior strongly so (T = 3.18), the gpt2 prior moderately (T = 2.24), the
ngram5_kn prior barely (T = 1.18). mean_neural_temperature is identical across the two priors, as it
must be -- p_neural does not depend on the prior model, so the same rows and the same folds select
the same temperature. Recorded as a verified consistency check.

Caveat, recorded rather than tidied away: this run emits sklearn overflow/divide-by-zero
RuntimeWarnings from fusion.reliability.fit_reliability_cv, which fits LogisticRegression on
unscaled reliability features. These are PRE-EXISTING and not caused by calibration -- the same
estimator on the uncalibrated dev frame emits 354 such warnings (checked directly). The arbitration
gate's own classifier scales its features per fold for exactly this reason; the reliability
estimator, inherited unchanged from the primary analysis, does not.
